# Plan

agentic-runtime は、一つのタスクを順序付きのステップからなるワークフローに従って完了へ運ぶ。

- ワークフローは YAML が正本、ロール・チェックリスト・ナレッジは Markdown が正本
- 各ステップの仕事はメインエージェントが担い、完了コマンドで次のステップへ進む
- plugin が持つのは CLI とコアだけである。アセットは利用リポジトリが持つ

カタログに依頼を担うワークフローがなければ新規作成、既存のワークフローを変更するなら[改善](#ワークフローを改善する)として扱う。作ったワークフローでタスクを進めるときは `agentic-runtime:execute` に従う。

## 何をどこへ書くか

| アセット | 担うもの | 置き場所 |
|---|---|---|
| ワークフロー | タスク全体の進め方と各ステップの仕事 | `.agents/workflows/*.{yaml,yml}` |
| ロール | 任意の役割と、その役割で守ること | `.agents/agents/**/*.md` |
| スキル | 再利用できる手順 | `.agents/skills/**/SKILL.md` |
| チェックリスト | セルフチェックする項目の並び | `.agents/checks/**/*.md` |
| ナレッジ | 判断の拠り所になる知見と規約 | 任意（既定の置き場は `wiki/**/*.md`） |
| ルール | ワークフローやステップをまたいで共有する決まりとリファレンス | `.agents/rules/*.md` または `wiki/**/*.rule.md` |

- ワークフローには順序付きの `steps` と、任意の `rules` を書く。各ステップには `name`・`description`・任意の `agent`・`using`・`read`・`checks`・`rules`・`artifacts`・`approval` を書く。
- `description` には何を明らかにする・作る・変える・確かめるステップかを書く。担当者、前後のステップ名、操作手順は書かない。
- ロールには役割、判断すること・しないこと、ステップを横断して守ることを書く。
- スキルには起動条件、前提、操作順を書く。記入式のテンプレートだけのために薄いスキルは作らない。
- ナレッジには対象領域の用語・構造・不変条件・規約と具体例を書く。
- テンプレートは `wiki/templates/<名前>.md` へ置き、ステップの `read` に同じ `wiki/templates/<名前>.md` と書く。
- 用語集は `wiki/terminology/<コンテキスト>.md` へ置き、ステップの `read` に同じ `wiki/terminology/<コンテキスト>.md` と書く。
- ルールは YAML フロントマターに任意の `using`・`read`・`checks`、本文に守ることを書く。ルール名はファイル名の `.md` または `.rule.md` を除いた部分から取るため、`name` は不要。項目がない場合もフロントマターには `{}` を書く。`agent` は指定しない。
- ルールは `.agents/rules/<名前>.md` または `wiki/<ドメイン>/<名前>.rule.md` に置く。同名のファイルが複数ある場合はエラーになる。
- ワークフローまたはステップの `rules` から、ルールの `name` を指定する。ワークフローのルールはすべてのステップへ、ステップのルールはそのステップだけへ適用する。

```markdown
---
using:
  - tdd
read:
  - wiki/coding-style.md
checks:
  - relevant-tests
---

変更はテストを先に書いて進める。
```

## ワークフロー YAML

```yaml
name: software-delivery
description: 設計から実装まで進める
rules:
  - agentic-runtime
steps:
  - name: 01-design
    description: 変更境界、期待する振る舞い、検証方法を合意して設計判断として残す
    agent: architect
    using:
      - grill-me
    read:
      - wiki/coding-style.md
    approval: required
    artifacts:
      - design.md
  - name: 02-implementation
    description: 合意した設計を実装して検証する
    rules:
      - development
    using:
      - tdd
    read:
      - 01-design/design.md
    checks:
      - relevant-tests
    artifacts:
      - summary.md
```

- `steps` は list で、上から順に実行する。ステップの `name` は `01-design` のように 1 始まりの位置 index を付け、その値がステップのディレクトリ名になる。
- `name` と `description` 以外は任意である。空の list や空の項目は書かない。
- `rules` はルール名を優先する順に並べる。同じルール名は最初の指定だけを残し、ステップのルールをワークフローのルールより先に適用する。
- `agent` を省いたステップは、追加の役割を与えずメインエージェントが実行する。`using` と `read` は `agent` なしでも使える。
- `using` はスキルの論理名で指す。
- `read` は利用リポジトリルートからの相対パス、または前のステップが `artifacts` で宣言した `<step-name>/<artifact>` を指す。置き場も拡張子も問わないが、絶対パスと `..` は指せない。前の成果物は自動では加わらない。
- glob で宣言した成果物を読む場合は、例えば `01-analysis/reports/*.md` のように宣言そのものを `read` に書く。完了時に記録された一致 file が指示へ展開される。
- `checks` は全ての項目にチェックが付くまで完了を阻む。`artifacts` は全て存在するまで完了を阻む。
- 人間の承認が要るステップだけ `approval: required` と書く。承認者本人の発言は完了コマンドへ渡す。

ワークフローは直線的に進む。完了コマンドが進行中のステップを完了し、次の Stop Hooks が次のステップを開始してその指示を渡す。指示は一つのステップにつき一度だけ届く。最後のステップを完了したあとは、Hooks がタスクをクローズする。

## ステップの境界と命名

依頼者が明示した段階と順番をステップの境界にする。各段階の中の操作、待機、検査、承認、再試行はそのステップに含める。依頼者が段階を示していない場合だけ、目的までの最短の流れを一案示して確認する。

ワークフロー名は達成する目的を表す kebab-case にする。ステップ名は `<index>-<自然名>` とし、一覧だけで何をするか伝わる最短の自然な名前にする。

## ワークフローを改善する

実走で起きた摩擦、手戻り、判断の不安定さから不足を特定する。操作数、一般的な工程名、将来の可能性だけでステップの境界を変えない。ワークスペース、会話、Pull Request、Git 履歴は観測として参照できるが、秘密情報や一回限りの値をワークフローやナレッジへ書き写さない。

カタログのワークフローやチェックリストを改善する場合は、実行中のタスクを完了したあとにカタログを変え、新しいタスクで検証する。チェックを弱めて通過させない。
